# Аналитика работы OnlyPlans

## Подключение один раз

Скопируйте из комплекта `.agents`, `scripts/journal.mjs`, `docs/analytics.md`, `.github/workflows/analytics.yml` в корень OnlyPlans с сохранением существующих файлов. Содержимое AGENTS.append.md ДОБАВЬТЕ в корневой AGENTS.md (создайте его, если отсутствует). Сам AGENTS.append.md переносить не нужно. При совпадении имён объедините изменения вручную. Изменения оформите отдельным PR. Требуется Node.js 22+; внешние npm-пакеты не нужны. В Codex скилл лежит в проектной `.agents/skills`, отдельная установка каждому не нужна. После обновления репозитория откройте новую сессию агента. Другим агентам явно дайте прочитать AGENTS.md и файл скилла: автоматическое обнаружение зависит от продукта.

Администратор GitHub должен сделать проверку `Analytics` обязательной для основной ветки через branch protection/ruleset и запретить прямой обход PR. Точное имя проверки возьмите из первого запуска Actions. Это действие выполняется в настройках GitHub, файла workflow для принудительного соблюдения недостаточно.

## Что учитываем

Личный постоянный идентификатор — GitHub handle, без email и пробелов. Одна сессия — один непрерывный рабочий отрезок одного участника и чата; при перерыве завершить, при возвращении начать новую. Несколько агентов одновременно — отдельные сессии; сумма их времени может превышать рабочее время человека. duration_sec — календарное время от запуска до закрытия, включая ожидание, а не доказательство активной работы. Время UTC, локальное представление возможно при анализе.

Три обязательных журнала находятся вместе в `analytics/<handle>/sessions/<id>.json`: поля работы/времени/токенов, массив decisions, массив capabilities. Пустой массив решений допустим после проверки агентом. Нельзя сочинять решение ради заполнения. Моды = реально применённые режимы агента (например plan); пишите также навыки, плагины, MCP и инструменты, включая встроенные. Не записывайте просто установленные плагины. Инвентаризация доступного софта — другая задача.

## Начало работы

Дайте агенту команду:

> Прочитай AGENTS.md, docs/analytics.md и .agents/skills/project-journal/SKILL.md. Мой идентификатор — HANDLE. Веди обязательные журналы в файлах проекта: сессия, решения, использованные моды/скиллы/плагины. Начни сессию сейчас, обновляй по ходу и закрывай перед передачей результата. Если точных токенов нет, укажи unavailable, не выдумывай. Задача: …

Агент выполняет из корня проекта (заменяет HANDLE и значения):

```sh
node scripts/journal.mjs start HANDLE "Задача" "Агент / модель или unknown"
```

Команда печатает ID. В следующих командах заменить SESSION на этот ID:

```sh
node scripts/journal.mjs use SESSION mode "Режим работы" "Для чего"
node scripts/journal.mjs use SESSION skill project-journal "Ведение аналитики" v1
node scripts/journal.mjs decision SESSION "Контекст" "Выбор" "Альтернативы" "Почему" "Последствия"
node scripts/journal.mjs use SESSION plugin "Имя" "Для чего" "Версия или unknown"
```

Существенные решения: выбор технологии, изменение требований, архитектура, компромисс качества и сроков, отказ от подхода. Пишите коротко. Общепроектное архитектурное решение дополнительно можно вынести в ADR и указать путь в записи; личный журнал остаётся обязательным.

## Токены

По умолчанию `{source: unavailable, total: null}`. Это честная запись отсутствующих данных, а не ноль. Для точного учёта каждый участник должен иметь экспорт usage своего агента/API, соответствующий именно этой сессии. Одной текстовой инструкцией получить недоступную телеметрию нельзя. Не читать приватные внутренние файлы приложений без отдельного согласования.

Если экспорт доступен, суммируйте только уникальные запросы этой сессии, не кумулятивные снимки; не добавляйте cached/reasoning повторно, если они уже входят в total. Укажите источник и охват. Сырые чаты и экспорты с чувствительными данными в Git не кладите.

```sh
node scripts/journal.mjs tokens SESSION reported 12345 "Экспорт usage; запросы A–D; total; без дублей"
node scripts/journal.mjs tokens SESSION estimated 800 "Оценка только видимых 1600 символов / 2; скрытый контекст не учтён"
```

Второй вариант допустим только как явно ограниченная оценка, не как расход оплаченных токенов. Отчёт разделяет reported и estimated, показывает количество unavailable. Для обязательного ТОЧНОГО учёта сначала согласуйте единый инструмент с экспортом usage; этот комплект не притворяется универсальным сборщиком телеметрии.

## Завершение и Git

Перед финальным ответом агент проверяет оба массива и выполняет:

```sh
node scripts/journal.mjs close SESSION "Что сделано, что проверено, что осталось"
node scripts/journal.mjs check
node scripts/journal.mjs report
```

close подтверждает, что журналы решений и инструментов просмотрены. При продолжении начать новую сессию. Добавьте JSON в тот же PR, что и работу; полностью бескодовые сессии — отдельным PR в конце дня. В PR перечислите участников и ID сессий. Не включайте секреты, полные переписки и персональные данные: Git хранит историю удалённого текста.

Если чат оборвался, при возвращении завершите старую запись командой `close SESSION "Восстановлено после обрыва; фактический конец неизвестен" interrupted`. Время будет до момента восстановления и завышено; не используйте такую запись как активное рабочее время. Не подделывайте точное время задним числом. Затем откройте новую.

CI проверяет структуру всех записей и наличие хотя бы одного изменённого закрытого журнала в PR. Это не доказывает полноту инструментов, точность токенов или участие каждого автора. Ревьюер проверяет записи каждого участника, осмысленность решений, источники токенов, отсутствие секретов и соответствие задаче. Удалять или переписывать прошлые записи без объяснения в PR нельзя. Ветка без PR и действия вне репозитория не покрываются этой проверкой.

## Ответственные

Каждый участник отвечает за свой журнал; агент помогает заполнять. Ревьюер проверяет его вместе с кодом. Координатор раз в неделю запускает `node scripts/journal.mjs report`, разбирает пропуски и незакрытые сессии, не смешивает оценки с точными токенами и не трактует календарное время как продуктивность. Таблица также появляется в Summary каждого запуска GitHub Actions. Состав участников и экспорт usage требуют согласования команды; не создавайте фиктивные записи за других людей.

## Совместимость с существующими журналами

Протокол docs/logging.md и scripts/session.ps1 сохраняется. До работы открой обе записи и укажи парные ID в результате. Не складывай показатели парных записей и не переписывай исторические logs/. Новый отчёт читает только analytics/; исторические PowerShell-сессии в него не входят. Оценки разрешены только по явному запросу пользователя, как требует проектный навык.
