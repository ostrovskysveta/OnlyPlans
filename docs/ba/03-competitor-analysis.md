# OnlyPlans — Детальный конкурентный анализ
> Версия 2.0. Дата актуализации: 2026-11-17. Анализ основан на публичной документации и страницах продуктов. Это desk research, а не hands-on тестирование. «Не подтверждено» означает, что функция не описана в изученных источниках или не совпадает по семантике, а не обязательно отсутствует в продукте.

## 1. Цель и методика

Цель — понять, какие решения OnlyPlans стоит перенять, где аналоги сильнее и в чём может состоять дифференциация продукта.

Сравниваем не абстрактный набор функций, а соответствие доменной модели OnlyPlans:

**Роадмап → Инициатива → Фича → Этап → Задача.**

Ключевые требования OnlyPlans:
- исследовательская инициатива может завершиться без фичи;
- этапы определяются отдельно для каждой фичи;
- типы и статусы задач — общие на уровне роадмапа и настраиваемые;
- терминальные статусы фиксируют веховые события;
- одна задача хранится один раз и может отображаться в нескольких представлениях;
- видимость задачи в представлении персональная и не влияет на доступ;
- у задачи может быть несколько исполнителей;
- пересечения считаются отдельно по исполнителю в рабочих днях;
- роли действуют в контексте роадмапа, а назначенный читатель может менять статус своей задачи;
- параллельное редактирование не должно приводить к незаметной перезаписи.

Критерии:
1. Доменная иерархия и гибкость декомпозиции.
2. Разделение типа, статуса, этапа и вехи.
3. Представления и модель общих данных.
4. Персональные настройки отображения.
5. Планирование по срокам, зависимости и календарь.
6. Назначения, несколько исполнителей и пересечения.
7. Права доступа и контекстные разрешения.
8. Аудит и защита от конфликтов.
9. Простота внедрения и администрирования.
10. Self-hosting, API, расширяемость и стоимость владения.

## 2. Сводный вывод

| Продукт | В чём особенно силён | Главный компромисс относительно OnlyPlans | Роль для анализа |

| OpenProject | Зрелое проектное планирование, типы работ, Gantt, зависимости, team planner, роли | Более тяжёлая PM-система; гибкость и мощь повышают сложность конфигурации; не та же модель «фича со своими этапами» | Референс для планирования, календаря, зависимостей и прав |
| Vikunja | Простая модель проектов и задач, общие задачи в нескольких видах, Gantt, Table, Kanban, self-host | Меньше возможностей для сложного продуктового планирования и ресурсного управления; персональные настройки вида не равны персональной видимости каждой задачи | Референс простоты и разделения данных/представлений |

| Weeek | Низкий порог входа, задачи/подзадачи, календарь, Gantt, приватность, роли, отчёты | Фокус на универсальном таск-менеджменте; публично описанные роли и доступы не подтверждают нужное точечное право «назначенный читатель меняет только статус» | Референс повседневного UX и простых командных сценариев |

Ни один продукт не следует объявлять «не умеющим» функцию только потому, что она не нашлась в публичной документации. Сравнение ниже показывает подтверждённые возможности и пробелы соответствия.

## 3. Plane

### Что хорошо
- Work item — единая базовая сущность с типом, статусом, приоритетом, исполнителями, датами, оценкой, родителем и связями.
- Тип work item позволяет задавать собственные поля под разные классы работ.
- Состояния проекта настраиваются и группируются по семантическим группам (backlog, unstarted, started, completed, cancelled).
- Modules группируют work items вокруг общей цели/фичи и имеют lead, members, dates и progress.
- Один work item может относиться к нескольким modules, что полезно для сквозных срезов.
- Views — сохранённые конфигурации фильтров, сортировки, layout и отображаемых полей. Есть project/workspace/teamspace scopes.
- Есть List, Board, Calendar, Table и Gantt/Timeline-подобные представления, фильтры и группировки.
- Есть роли Admin, Contributor, Commenter, Guest; отдельно управляются права на work items, views, modules и другие области.
- Встроены страницы/документация, intake, cycles, milestones, releases, worklogs, audit logs; набор функций можно включать по проекту.
- Есть API, webhooks, интеграции и варианты self-hosting.

### Что требует внимания / ограничения для OnlyPlans
- Module — контейнер/группировка работ по цели, а не этап, который обязательно принадлежит одной фиче и содержит следующий уровень задач.
- Initiative в Plane позиционируется как более высокий уровень координации между проектами; это не тождественно инициативе OnlyPlans, которая может быть исследовательской и завершиться без фичи.
- State — состояние work item, а не этап фичи. При переносе модели нельзя подменять одно другим.
- Private view скрывает саму сохранённую конфигурацию от других участников, но это не то же самое, что персонально скрыть конкретную задачу в конкретном представлении, сохранив общий view.
- Роли дают широкие наборы полномочий. Точное контекстное разрешение «читатель может менять статус только назначенной ему задачи, но не другие поля» в изученной матрице не подтверждено.
- Большая функциональная поверхность может оказаться избыточной для команды 4–30 человек, если нужны только roadmap, этапы, задачи и календарь.
- Self-hosted возможности, редакции и состав функций следует проверять по актуальной лицензии и выбранной поставке; не переносить коммерческие возможности в расчёт бесплатной редакции без проверки.

### Что взять в OnlyPlans
1. Универсальную сущность задачи с чётко описанными полями и связями.
2. Настраиваемые типы задач и наборы полей, но не допускать бесконтрольного создания сотен полей.
3. Сохранённые views с фильтрами и группировками.
4. Разделение связей parent-child, related и dependency.
5. Гибкую конфигурацию функций, но с простым MVP-профилем.
6. Историю изменений и API-first подход.

## 4. OpenProject

### Что хорошо
- Work packages — зрелая модель единиц планирования с типами, статусами, атрибутами и пользовательскими полями.
- Типы work packages могут быть включены/выключены в конкретном проекте; для типов можно задавать отображение в roadmap и признак milestone.
- Есть иерархия родитель–потомок и отдельные типы отношений: predecessor/successor, blocks/blocked by, relates to и др.
- Gantt поддерживает сроки, drag-and-drop, связи, иерархию, вехи и визуальные предупреждения о расхождении дат родителя и потомков.
- В автоматическом режиме зависимость может сдвигать последующую работу; в ручном — сохранять связь без автоматического изменения дат.
- Team planner показывает задачи по строкам исполнителей, позволяет переносить и переназначать их.
- Есть настройка рабочих дней, часов и нерабочих дат; по умолчанию рабочая неделя — понедельник–пятница.
- Роли и права настраиваются на уровне проекта; пользователю могут назначаться несколько ролей.
- Можно строить достаточно строгие процессы с большим количеством правил и полей.

### Что требует внимания / ограничения для OnlyPlans
- Модель work package универсальна, но требует от команды самой договориться, какие типы означают инициативу, фичу, этап или задачу. Это создаёт риск семантической неоднородности.
- Этапы фичи как отдельный обязательный уровень не являются базовым концептом: их можно моделировать типами/родителями, но это не та же доменная конструкция.
- Автоматическое перепланирование зависимых задач полезно в классическом project management, но опасно для OnlyPlans как скрытое изменение плана. В MVP OnlyPlans лучше ограничиться предупреждениями.
- Настройка рабочих дней/нерабочих дат на уровне экземпляра влияет на все проекты; изменение календаря способно пересчитать сроки массово. Для OnlyPlans это слишком сильная глобальная настройка на раннем этапе.
- Богатая система модулей, ролей, полей и связей увеличивает порог внедрения и администрирования.
- Важные функции и расширения могут зависеть от редакции; перед сравнением затрат нужно отдельно проверить Community и Enterprise.

### Что взять в OnlyPlans
1. Разделять иерархию и зависимости — это разные отношения.
2. Показывать расхождение сроков фичи/родителя и дочерних работ, не исправляя их автоматически.
3. Взять идею team planner: календарная проекция по исполнителям.
4. Учитывать рабочие дни при расчётах.
5. Сделать матрицу прав явной и проектно-специфичной.
6. В перспективе добавить режимы ручного/автоматического планирования только после подтверждения спроса.

## 5. Vikunja

### Что хорошо
- Очень ясная базовая модель: проект содержит задачи, а views определяют, как их показывать.
- В одном проекте доступны List, Table, Kanban и Gantt; пользователь может создавать дополнительные views и задавать им фильтры.
- Изменение задачи в одном представлении отражается в других, потому что views не владеют задачами.
- Поддерживаются вложенные проекты, подзадачи, несколько исполнителей, labels, priority, даты, комментарии, вложения и связи задач.
- Gantt отображает подзадачи группами, суммарную полосу родителя и стрелки зависимостей.
- Есть сохранённые фильтры на несколько проектов.
- Проект можно расшарить пользователю, команде или по ссылке; предусмотрены Read, Read & Write и Admin.
- Есть self-hosting и относительно компактная концепция продукта.

### Что требует внимания / ограничения для OnlyPlans
- Сохранённое состояние вида может храниться локально в браузере/desktop app и не переноситься между устройствами; это не подходит для персональной серверной настройки видимости, если требуется единое поведение на всех устройствах.
- Вид проекта и его фильтры — общие для участников; Saved Filters — персональные межпроектные запросы. Это два разных механизма, и ни один не следует путать с требуемой моделью user + view + task visibility.
- Gantt view, согласно документации, имеет ограничения по фильтрации. Это снижает гибкость сложных календарных сценариев.
- Права в основном укрупнённые: Read, Read & Write, Admin. Точечное право менять только статус назначенной задачи не подтверждено.
- Встроенная модель статусов сравнительно проста; нет подтверждённой семантики произвольных статусов как веховых событий с отдельной историей достижения.
- Нет подтверждённого специализированного слоя для продуктовых инициатив, фич и этапов с индивидуальной конфигурацией этапов каждой фичи.

### Что взять в OnlyPlans
1. Самое важное: view не владеет задачей, задача существует независимо от представления.
2. Не копировать задачи ради разных срезов.
3. Сделать фильтры и виды простыми для создания.
4. Сохранить понятные дефолтные представления, но позволить настраивать свои.
5. Явно отделить общие настройки view от персонального состояния/видимости пользователя.

## 6. Kaiten

### Что хорошо
- Сильная визуальная модель Kanban и управление потоком работы.
- Поддерживаются доски, дорожки, типы карточек, ограничения потока и автоматизации.
- Есть отдельный модуль Gantt и ресурсного планирования.
- На Gantt отображаются этапы, задачи, вехи и ресурсы; можно задавать связи между задачами.
- Ресурсное планирование опирается на рабочие часы, доступные часы сотрудника и календарь.
- Можно анализировать перегрузку и простои, если данные о трудоёмкости и доступности заполнены.
- Есть развитые возможности для командного управления и разные модули под разные процессы.

### Что требует внимания / ограничения для OnlyPlans
- Сильная сторона Kaiten — управление потоком и ресурсами, а не обязательно продуктовая доменная модель. Необходимо проверить, насколько удобно моделировать «инициатива → фича → индивидуальные этапы → задачи» без сложных обходных конструкций.
- Точная семантика «одна задача в нескольких представлениях с персональной видимостью по каждому view» не подтверждена просмотренными материалами.
- Ресурсное планирование требует более точных оценок часов, доступности и календарей. Для OnlyPlans нельзя показывать числовую загрузку как факт, если известны только даты и исполнители.
- Модульная тарифная модель: Gantt, ресурсное планирование, автоматизации, ограничения и другие возможности могут быть отдельными модулями/опциями. Нужно считать стоимость полного сценария, а не базового тарифа.
- Большое количество настроек может быть избыточно для небольших команд без выделенного администратора процесса.
- Для OnlyPlans важно не перенимать визуальную сложность ресурсного планирования раньше, чем появятся оценки трудозатрат и календари сотрудников.

### Что взять в OnlyPlans
1. Визуальное представление задач по исполнителям.
2. Связь календарного плана с зависимостями.
3. Принцип: ресурсная загрузка достоверна только при наличии данных о трудоёмкости и доступности.
4. Возможность настраивать рабочий процесс без жёсткого универсального workflow.
5. Не переносить почасовую загрузку в MVP.

## 7. Weeek

### Что хорошо
- Низкий порог входа и широкий набор привычных режимов: список, доски, неделя, месяц, Gantt.
- Есть задачи и подзадачи, исполнители, связи между задачами, кастомные поля, теги, комментарии, вложения и учёт времени.
- Есть проекты, портфели и шаблоны, что помогает структурировать работу.
- Доступы можно настраивать на уровнях портфеля, проекта и доски; доступны владелец, редактирование, комментирование, просмотр и отсутствие доступа.
- Есть приватные задачи и приватные пространства/объекты.
- Есть пользовательские роли на более высоком тарифном уровне.
- Отчёты, выгрузки и автоматизации закрывают типовые задачи менеджмента.
- Поддерживаются интеграции с календарями.

### Что требует внимания / ограничения для OnlyPlans
- Weeek — универсальный таск-менеджер; инициативы, фичи и индивидуальные этапы фичи не являются явно описанной базовой доменной моделью.
- Наследование доступа от родительских портфелей/проектов удобно для администрирования, но это другая задача, чем персональная видимость задачи в конкретном представлении.
- Приватность объекта — не то же самое, что скрытие задачи только из одного календарного представления у одного пользователя.
- В публичной документации не подтверждено точечное разрешение назначенному читателю менять только статус назначенной задачи.
- Часть продвинутых настроек доступов и пользовательских ролей доступна только на старших тарифах.
- В пользовательских отзывах встречаются замечания к удобству общего календарного планирования встреч; отзывы единичны и не доказывают системную проблему, но сценарий общего календаря стоит проверить на практике.

### Что взять в OnlyPlans
1. Понятные режимы отображения и доступность календаря для повседневной работы.
2. Низкий порог создания задач и подзадач.
3. Комментарии и вложения рядом с объектом.
4. Простые уровни доступа «просмотр / комментирование / редактирование».
5. Проверить, как приватные задачи влияют на поиск, календарь, уведомления и связанные объекты.

## 8. Сравнительная матрица по ключевым сценариям

Обозначения:
- **Да** — возможность прямо описана в изученной документации.
- **Частично** — есть близкий механизм, но семантика или охват отличаются.
- **Не подтверждено** — в изученных публичных материалах не найдено достаточного подтверждения.
- Это не абсолютная оценка качества продукта.

| Возможность | Plane | OpenProject | Vikunja | Kaiten | Weeek |
|---|---|---|---|---|---|
| Настраиваемые типы задач | Да | Да | Частично | Да/проверить детали | Да, кастомные поля/типы проверить |
| Настраиваемые статусы | Да | Да | Частично | Да | Да |
| Отдельный уровень этапов фичи | Частично (Modules) | Частично (иерархия/типы) | Частично (проекты/подзадачи) | Частично (доски/дорожки) | Частично (доски/подзадачи) |
| Одна задача в нескольких views | Да | Частично (одни work packages в разных модулях/планировщиках) | Да | Не подтверждено в требуемой семантике | Частично |
| Персональная видимость задачи по view | Частично (private view, не per-task visibility) | Частично (private team planner) | Частично (локальное состояние view / personal filters) | Не подтверждено | Частично (приватность объектов, не per-view) |

## 9. Основные продуктовые выводы для OnlyPlans

### 9.1. Не конкурировать количеством функций
У зрелых аналогов больше интеграций, автоматизаций, отчётов, типов представлений и административных возможностей. Повторение этого набора приведёт к расползанию MVP.

### 9.2. Дифференциация — в предметной модели, а не в календаре
Календарь, Gantt, Kanban, подзадачи, зависимости и фильтры уже широко представлены. Потенциальная ценность OnlyPlans — корректная связка продуктового намерения и плана исполнения:
- инициатива может быть исследованием без фичи;
- у каждой фичи свой набор этапов;
- тип и статус задачи не подменяют этап;
- одна задача видна в нескольких срезах без дублирования;
- персональная видимость не меняет общие данные и права.

### 9.3. Видимость и доступ должны быть отдельными понятиями
У аналогов есть приватные задачи, приватные views, фильтры и уровни доступа, но это разные механизмы. OnlyPlans должен явно разделить:
- право пользователя открыть объект;
- включение задачи в конкретное представление;
- персональное скрытие задачи из этого представления.

### 9.4. Пересечения — не ресурсная загрузка
Kaiten и OpenProject показывают ценность планирования по людям, рабочим календарям и ресурсам. Но они опираются на более богатые данные. В MVP OnlyPlans достаточно:
- полосы задачи по каждому исполнителю;
- отметки пересечения хотя бы на один рабочий день;
- исключения выходных;
- отдельного отображения неназначенных задач.
Не называть это «процентом загрузки» и не делать вывод о перегрузке.

### 9.5. Не копировать сложность зрелых систем
OpenProject и Kaiten демонстрируют, насколько далеко может зайти настройка процессов. OnlyPlans нужен управляемый уровень конфигурируемости: этапы на уровне фичи, справочники на уровне роадмапа, представления и персональная видимость. Произвольные конструкторы workflow, скрипты и сложные права не нужны в первом релизе.

## 10. Рекомендации для дальнейшего развития

### MVP — оставить в фокусе
- Иерархию инициатива → фича → этап → задача.
- Настройку этапов для каждой фичи.
- Справочники типов и статусов на уровне роадмапа.
- Веховый признак статуса и историю достижения.
- Общие задачи в нескольких представлениях.
- Персональную видимость задачи по view.
- Ролевые и контекстные права.
- Несколько исполнителей и визуальные пересечения по рабочим дням.
- Версионирование/optimistic locking при сохранении.

### После MVP — изучить по подтверждённому спросу
- Сохранённые фильтры и группировки уровня Plane/Vikunja.
- Командный планировщик по строкам исполнителей уровня OpenProject.
- Ресурсную загрузку уровня Kaiten — только при наличии оценок трудоёмкости и рабочих календарей.
- Шаблоны этапов и задач.
- API и webhooks.
- Импорт/экспорт и интеграции.

### Не делать без доказанной потребности
- Полноценный BPMN/workflow-конструктор.
- Автоматическое каскадное перепланирование.
- Почасовую загрузку и прогноз capacity без оценок.
- Сложную матрицу ролей на десятки разрешений.
- Повторение всех модулей универсальных PM-систем.

## 11. План практической проверки конкурентов

Публичная документация не заменяет hands-on тестирование. Перед окончательным позиционированием рекомендуется провести короткий PoC на Plane, Vikunja и OpenProject, а Kaiten и Weeek проверить как коммерческие UX-референсы.

Единый тестовый сценарий:
1. Создать инициативу «Проверить гипотезу» без фичи и завершить её.
2. Создать инициативу с двумя фичами.
3. Для каждой фичи создать свой набор этапов.
4. Добавить задачу в два представления.
5. Скрыть задачу только для одного пользователя и только в одном представлении.
6. Назначить задачу двум исполнителям.
7. Проверить пересечения по каждому исполнителю и поведение на выходных.
8. Выдать пользователю read-only доступ и назначить его на задачу; проверить, может ли он менять только статус.
9. Одновременно открыть задачу двумя редакторами и проверить конфликт сохранения.
10. Проверить экспорт данных, API, self-host, аудит и ограничения лицензии.

Фиксировать для каждого шага: число кликов, необходимость обходной модели, понятность терминов, сохранение общей записи, корректность прав, результат и тарифное ограничение.
